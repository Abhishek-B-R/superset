Automations: three issues, and what to test

Three tickets that only make sense together. The list can stop being a triage queue once failures have somewhere to go, and agents can stop claiming they set up a trigger once there is a tool that sets one.

PR #7773 SUPER-2226 · SUPER-2227 · SUPER-2231 3 commits · 32 files branch: automations-list-runs-and-agent-triggers

An agent could never create an event trigger

SUPER-2231 · packages/mcp, packages/cli, plugins/superset

What was wrong

grep trigger across the MCP and CLI automation commands returned nothing at all. The server schema has accepted a full triggers[] array the whole time; both agent surfaces exposed only rrule, and marked it required.

So an agent asked for “run this when someone opens a PR” had no tool for it and, having no way to fail, reported success. That is the bug behind “the agent said it set up a trigger and it didn’t show up”.

What changed

  • triggers on automations_create and automations_update, carrying the per-kind shape in its description — an MCP client sees the discriminated union only as “object”.
  • rrule and timezone become optional. An automation needs a schedule or a trigger set.
  • automations_trigger_options and superset automations trigger-options resolve provider ids, because a scope stores ids and never names.
  • --triggers / --triggers-file on the CLI, validated locally so a typo names the offending path.
  • The automate skill covers events, and says a trigger write replaces the whole set.

Failures could only be found one automation at a time

SUPER-2227 · packages/trpc, packages/db, apps/desktop

What was wrong

Run history was per-automation only. automation.listRuns takes an automationId, and the run list lives on the detail page, so finding a failure meant already knowing which automation it belonged to.

That is also what blocked SUPER-2226: you cannot take failure triage off the list until it has somewhere else to live.

What changed

  • automation.listOrgRuns — one org’s history, newest first, keyset-paginated on (createdAt, id) so rows don’t repeat or skip as runs arrive under an open screen.
  • automation.runPayload — the provider body, fetched only when a row is expanded, scoped on the run so a foreign run id reads as absent.
  • Multi-select → “Run again”, deduplicated by automation and owner-gated to match what runNow accepts.
  • Migration 0121: an (organization_id, created_at) index on automation_runs.

The list reordered itself around failures

SUPER-2226 · apps/desktop

What was wrong

Three sections — needs attention, up next, paused — with failed automations pinned to the top and the rest sorted by nextRunAt. Rows moved as time passed, so an automation was wherever its last run had put it rather than where you left it.

What changed

  • One section, in createdAt desc order. A row stays put between visits.
  • Red row text, per-row failure tooltips and “Retry all” are gone. The status dot and label stay.
  • The Failed stat card keeps its count and links into All runs, filtered.
  • “New automation” is a split button: main click creates directly, “Create with AI” moves into the chevron.
  • The sidebar failure badge is acknowledged on All runs instead of here.

One behaviour change beyond the tickets. The sidebar failure badge used to clear when you opened the automations list. After 2226 that list no longer shows failures, so clearing it there would spend the signal before anyone saw what it pointed at. It now clears on All runs.
