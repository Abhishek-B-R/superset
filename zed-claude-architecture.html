One panel, many agents

1The shape: two objects carry everything

The whole design rests on two objects. Rc<dyn AgentConnection> is the agent — whichever one. Entity<AcpThread> is the conversation — a flat timeline of user messages, assistant messages, thoughts, tool calls, plans, and permission prompts. The Agent Panel is written entirely against those two types; it holds no enum of known agents and no per-agent view code.

Both connection types drive the same AcpThread, so every feature — streaming, tool cards, diffs, embedded terminals, permission buttons, token meters — is built once and works for all agents.

2The core trick: the protocol is the internal API

AcpThread accepts exactly one input type: acp::SessionUpdate — the wire message external agents send over stdio (message chunks, thought chunks, tool calls, plan updates, usage updates, mode changes). Zed's native agent doesn't get a private path into the UI; it synthesizes the same wire messages and pushes them through the same handler. It is a client of its own protocol: 

// crates/agent/src/agent.rs — the NATIVE agent publishing its slash commands
session.acp_thread.update(cx, |thread, cx| {
    thread.handle_session_update(
        acp::SessionUpdate::AvailableCommandsUpdate(
            acp::AvailableCommandsUpdate::new(available_commands.clone()),
        ),
        cx,
    )
});

This is what makes "one UI, many agents" cheap: there is exactly one timeline renderer because there is exactly one input type. Anything the native agent wants to display, it must be able to express in ACP terms — which keeps the protocol honest, because Zed's own agent is its most demanding consumer.

3AgentConnection: capabilities as values, not variants

The trait in crates/acp_thread/src/connection.rs has a small mandatory core and a long optional tail. Trimmed: 

pub trait AgentConnection {
    // mandatory
    fn agent_id(&self) -> AgentId;
    fn new_session(self: Rc<Self>, project, work_dirs, cx) -> Task<Result<Entity<AcpThread>>>;
    fn prompt(&self, params: acp::PromptRequest, cx) -> Task<Result<acp::PromptResponse>>;
    fn cancel(&self, session_id, cx);
    fn auth_methods(&self) -> &[acp::AuthMethod];
    fn authenticate(&self, method, cx) -> Task<Result<()>>;

    // capability probes (defaults: false / Err)
    fn supports_load_session(&self) -> bool { false }
    fn supports_resume_session(&self) -> bool { false }
    fn supports_logout(&self) -> bool { false }
    // …load_session, resume_session, close_session, logout…

    // optional capabilities (defaults: None)
    fn model_selector(&self, session_id) -> Option<Rc<dyn AgentModelSelector>> { None }
    fn session_modes(&self, session_id, cx) -> Option<Rc<dyn AgentSessionModes>> { None }
    fn session_config_options(&self, session_id, cx) -> Option<Rc<dyn AgentSessionConfigOptions>> { None }
    fn session_list(&self, cx) -> Option<Rc<dyn AgentSessionList>> { None }
    fn truncate(&self, session_id, cx) -> Option<Rc<dyn AgentSessionTruncate>> { None }
    fn retry(&self, session_id, cx) -> Option<Rc<dyn AgentSessionRetry>> { None }
    fn set_title(&self, session_id, cx) -> Option<Rc<dyn AgentSessionSetTitle>> { None }

    fn into_any(self: Rc<Self>) -> Rc<dyn Any>;   // the downcast pressure valve
}

Three complementary idioms express "what can this agent do", and the choice is deliberate:

  • Option<Rc<dyn Trait>> getters for session-scoped features — "does this agent+session have a model selector right now?" The UI calls the getter and renders the control only when it gets Some.
  • supports_*() → bool probes for questions the panel must ask before a session exists (can I reload history? can I sign out?).
  • Data-driven lists — auth_methods() and config_options() return plain vectors the UI renders verbatim; there is no enum of known auth flows or known settings.

Crucially, on the external side every one of these answers comes from the ACP handshake, not from code. AcpConnection derives them from the capability struct the agent returned at initialize: 

// crates/agent_servers/src/acp.rs — capabilities are protocol data
fn supports_load_session(&self) -> bool { self.agent_capabilities.load_session }
fn supports_resume_session(&self) -> bool {
    self.agent_capabilities.session_capabilities.resume.is_some()
}
fn supports_logout(&self) -> bool { self.agent_capabilities.auth.logout.is_some() }

For native-only features that make no sense in the protocol (tool-permission profiles, skills), the UI uses connection.downcast::<NativeAgentConnection>() rather than adding native-only trait methods — a pressure valve that keeps the trait from accreting.

4How per-agent differences render generically

The interesting question is never "can the panel show a message" — it's how it shows a model picker for five agents with five different model systems, or Claude Code's plan/accept-edits modes, without knowing any of them.

The single branch that decides the toolbar

There is exactly one place the composer toolbar's shape is decided, and it branches on capability presence, not agent identity: 

// crates/agent_ui/src/conversation_view.rs
// Config options take precedence over legacy mode/model selectors
if let Some(config_options) = connection.session_config_options(&session_id, cx) {
    config_options_view = Some(ConfigOptionsView::new(config_options, …));
    model_selector = None;
    mode_selector  = None;
} else {
    model_selector = connection.model_selector(&session_id).map(ModelSelectorPopover::new);
    mode_selector  = connection.session_modes(&session_id, cx).map(ModeSelector::new);
}
  • Native agent → a real AgentModelSelector backed by the LanguageModelRegistry (every provider's models, favorites, grouping), plus the native-only profile selector via downcast.
  • Claude Code / Codex / Cursor → the server returns configOptions in session/new, and the "model picker" is just a Select option whose category == Model. Zed renders a searchable picker for any Select and a switch for any Boolean — it never knows what the options mean.
  • Category metadata restores ergonomics: because an option carries category: Model | Mode | ThoughtLevel | ModelConfig, Zed attaches its real keybindings (toggle model selector, cycle modes, thinking-effort menu) to options declared by agents that have never heard of Zed's keymap.

Modes, slash commands, auth — same pattern

  • Modes (plan / accept-edits): the session returns { current_mode_id, available_modes }; the picker renders mode.name with mode.description as an aside. Changing it sends session/set_mode with optimistic local state and rollback on error; the agent can also push CurrentModeUpdate mid-turn (Claude Code does when you shift-tab in another client).
  • Slash commands: agents stream AvailableCommandsUpdate; the composer's /-completion menu is populated from it verbatim. The native agent publishes /compact and every MCP prompt through the identical message.
  • Auth: when a request fails with AuthRequired, the panel renders one button per entry in auth_methods() — descriptions as tooltips, nothing hardcoded. A terminal-type method spawns the agent's own CLI login (claude /login) inside a Zed terminal, and the thread auto-retries when it completes.
  • @-mentions degrade by capability: if the agent advertised embedded_context, mention content is inlined as an ACP embedded resource; otherwise it's sent as a zed://… resource link the agent can read back through fs/read_text_file. The same flags prune the @-menu itself and gate image paste.
Where the per-agent code actually lives grep for the four agent-id constants (claude-acp, codex-acp, gemini, cursor) finds production references in exactly two files, both in agent_servers — and every reference is an env var or a protocol stopgap: blanking ANTHROPIC_API_KEY for Claude Code (so it bills the user's subscription, never a stray shell key), passing CODEX_API_KEY through for Codex, injecting SURFACE=zed and resolving a Gemini key from Zed's keychain, synthesizing a terminal-login auth method for Gemini until Google ships official ones, and a parameterizedModelPicker capability flag for Cursor. The UI layer branches only on native-vs-not, and only for copy and icons.

6Where agents come from: registry + settings, zero built-ins

There is no built-in agent enum. Claude Code, Codex, Gemini, and Cursor are ordinary entries in a remote registry — cdn.agentclientprotocol.com/registry/v1/latest/registry.json, fetched hourly and cached locally. Each entry declares a version and a distribution: a platform-keyed binary archive (sha256-verified) and/or an npm package.

  • "Installing" an agent writes one settings line: {"agent_servers": {"claude-acp": {"type": "registry"}}}. Removing it deletes the key.
  • For npm distributions, Zed installs with its own managed Node runtime under a ceiling-range pin (pkg@0.0.0 - <registry version>), resolves the package's bin, and spawns node <adapter.js>. Binary distributions are downloaded, hash-verified, and content-addressed.
  • A fully custom agent is two settings lines — any command + args that speaks ACP on stdio: {"type": "custom", "command": "node", "args": ["~/my-agent/index.js", "--acp"]}.
  • Version bumps in the registry signal live connections to reconnect; the panel shows install progress and update nudges through the same store.

Net effect: adding a coding agent to Zed is a data change, not a release. The agent picker menu is simply "native agent" plus whatever the settings map contains, sorted by display name.

A handful of quirk-normalizers keep the common UI clean: optimistically-added user messages are deduped against agents that echo them back; Gemini's abort-on-cancel error is converted to a clean cancelled stop; mode/config changes apply optimistically and roll back on error so pickers never lag a click.

8Deep integration: buffers, terminals, permissions

What makes external agents feel native isn't the timeline — it's that Zed advertises client capabilities at the handshake and then serves them from the editor's own machinery:

  • File access goes through buffers, not the filesystem. fs/read_text_file reads the open buffer (unsaved edits included) and caches the snapshot it handed out; fs/write_text_file computes a minimal diff against that snapshot and applies it as a single anchored buffer transaction tagged as an agent edit — one undo step, attributable hunks in the review UI, format-on-save, then save. Unsaved user work is never clobbered.
  • Follow-the-agent. Tool calls carry file locations; Zed resolves them to buffer anchors and moves an agent cursor the editor can follow. Subagent sessions deliberately don't hijack your viewport.
  • Real terminals. terminal/create mounts an actual Zed terminal entity inline in the tool card — live output, kill, exit status over the protocol.
  • Permissions block on the wire. The JSON-RPC response to session/request_permission stays open on a oneshot channel until the user clicks; cancellation works in both directions.
  • Checkpoints for everyone. Every user message snapshots a git checkpoint before the prompt is sent, so any agent's turn — native or external — can be rewound, working tree and conversation together.

9The native agent & the model-provider stack

The native agent is the one implementation that talks to model APIs itself. Its loop (Thread::run_turn_internal) re-reads model, profile, and tool set every iteration, streams a completion, executes tool calls, feeds results back, and ends the turn when a response contains no tool calls — with auto-compaction past a token threshold, backoff retries, refusal-fallback to another model, and streaming edit_file edits that apply to the live buffer while the model is still emitting them.

Under it sits a four-crate provider stack (anthropic wire client → language_model_core types → language_model registry → language_models concrete providers), all normalized to one streamed event enum: 

pub enum LanguageModelCompletionEvent {
    Queued { position: usize },   // cloud only
    Started,                      // cloud only
    Stop(StopReason),             // EndTurn | MaxTokens | ToolUse | Refusal
    Text(String),
    Thinking { text, signature },
    ToolUse(LanguageModelToolUse),        // streamed live via repaired partial JSON
    StartMessage { message_id },
    UsageUpdate(TokenUsage),
    Compaction(CompactionUpdate),
    /* … */
}
  • Direct Anthropic: POST /v1/messages with X-Api-Key (env var or OS keychain, scoped to the API URL), SSE streaming, model list fetched from /v1/models with defaults picked by prefix ranking — no hardcoded model list. Prompt caching is automatic (5-minute tail plus 1-hour breakpoints on the last tool and system block); concurrency is a 16-permit semaphore per model app-wide.
  • Hosted zed.dev: the client builds the exact same Anthropic request JSON and ships it as an opaque provider_request blob to cloud.zed.dev/completions with a Zed-account token — the cloud is a thin auth/metering pass-through, so direct-key and hosted behavior share one conversion codepath. Its NDJSON stream adds queue-position and started status events.
  • Safety is layered and fail-closed: profiles (tool visibility) × regex allow/deny/confirm permissions with unbypassable hardcoded rules (rm -rf / variants, path traversal) × workspace trust × optional OS sandboxing. Inputs that defeat analysis — shell substitutions, invalid user regexes — deny rather than allow.
  • Rules files: first match per worktree from .rules, .cursorrules, .windsurfrules, .clinerules, .github/copilot-instructions.md, AGENT.md, AGENTS.md, CLAUDE.md, GEMINI.md; personal ~/.config/zed/AGENTS.md renders first so projects can override it.

10Design takeaways

  • Make the protocol the internal API. The native agent synthesizes the same SessionUpdate messages external agents send, so there is one timeline renderer and zero drift between "our agent" and "their agents". Your own agent should be the protocol's most demanding client.
  • Capabilities as values, not variants. Option<Rc<dyn Trait>> getters, supports_* probes, and verbatim-rendered lists — all derived from the handshake. Feature gaps degrade per-control instead of per-agent, and adding an agent is a settings entry.
  • Quarantine identity. Four agent-id constants, referenced in two files, only for env vars and protocol stopgaps — each annotated with the upstream issue that will delete it. The UI never branches on which agent it's hosting.
  • Generic mechanisms + category metadata. A model picker Zed has never seen still gets Zed's keybindings because the config option says category: Model — semantics travel with the data.
  • Editor-mediated file access. Snapshot-diffed buffer transactions make any agent's edits reviewable, one-step-undoable, and safe against clobbering unsaved work. The filesystem is never the API.
  • Registry-driven distribution. A CDN JSON plus one generic spawner (managed Node, sha256-verified binaries, ceiling-range pins) replaced all per-agent integration code. Shipping a new agent is a data change.
  • Downcast as the pressure valve. Native-only features (profiles, skills, rewind) reach the concrete type explicitly instead of polluting the shared trait — which also makes the roadmap legible: the features external agents lack are exactly the trait defaults AcpConnection hasn't overridden yet.

11Proposal: a Superset web chat over any running Claude/Codex session

The question: can we build a browser chat UI (Vercel AI SDK) that reaches, over a URL, any Claude Code or Codex session running in a Superset workspace — using ACP as the protocol? Yes, and every piece is already proven. Zed demonstrates the protocol works; the transport is trivially swappable (newline-delimited JSON-RPC doesn't care if it flows over stdio or a WebSocket); and the official adapters support attaching to existing sessions. Verified against the live ACP registry and the published adapter:

  • The registry serves @agentclientprotocol/claude-agent-acp@0.84.0 (built on the Claude Agent SDK) and @agentclientprotocol/codex-acp@2.0.0 — the same packages Zed spawns.
  • The Claude adapter's published code advertises loadSession: true and implements listSessions and resume — internally mapped to the Claude Agent SDK's resume/forkSession options over the on-disk session transcripts in ~/.claude/projects/.
The one catch: you attach to a session, not a process A Claude/Codex session running in a Superset terminal owns its stdio — nothing else can share it. What ACP gives you instead is resume by session id: the gateway spawns its own adapter process in the same workspace and calls session/load, which replays the full history from the shared on-disk transcript and continues the same conversation. That's the same session, same context, same files — a different process. Prompting the same session concurrently from the terminal and the web can fork its history, so the UX should be "take over" (or read-only mirror while the terminal is mid-turn), not simultaneous driving.

The gateway plays Zed's role: it is the ACP client. Superset already has the two hard parts — a host process next to every workspace, and authenticated URLs to reach it — so the new code is just the translator in the middle.

Scope, honestly

  • Gateway: ~300–400 lines — process spawn + ndjson framing, the update→part translator, a pending-permission map, session registry. No protocol invention; the agent-client-protocol schema package (or plain JSON) covers the types.
  • Web: a stock useChat page plus renderers for the tool, plan, and permission parts. History hydration comes free from session/load's replay.
  • Auth & placement: the gateway belongs beside the workspace (where Superset's host-service already runs), behind Superset's existing session auth — the adapter inherits the host's Claude login, so no credentials ever reach the browser.
  • Risks: concurrent terminal+web prompting can fork a session's history (design for take-over, not co-driving); permission UX must fail closed if the browser disconnects mid-request (gateway answers "reject" on timeout); adapter versions move fast — pin with a ceiling range the way Zed does.
